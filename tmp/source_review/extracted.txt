===== PÁGINA 2 =====
                Diseño de una API para gestionar Cursos y Matrículas


1. Objetivo y alcance
Diseñar una API REST que permita a una institución educativa administrar sus cursos y las
matrículas de sus estudiantes. La API se expone sobre HTTPS, usa JSON como formato de
intercambio, está versionada (/api/v1) y sigue los principios REST: recursos identificados por
URI, uso semántico de los métodos HTTP y códigos de estado estándar.

Estilo arquitectónico: cliente-servidor y sin estado (stateless). Se implementa como un monolito
en Laravel (PHP): una sola aplicación y base de datos, organizada por recurso con rutas,
controladores, modelos, resources (formato JSON) y middleware (autenticación y roles). Se
eligió un monolito porque el alcance es pequeño y la matrícula necesita una transacción única
(validar cupo, registrar y descontar). El contrato de la API queda descrito en este documento.

2. Recursos de la API
Cada recurso se nombra en plural y en minúsculas. Las relaciones se expresan con
identificadores.

 Recurso      Descripción                Atributos principales
 estudiantes   Personas que pueden            id, documento, nombres, apellidos, correo,
                matricularse en cursos.       programa, estado
 docentes      Profesores responsables de     id, nombres, apellidos, correo, departamento
                  dictar los cursos.
 cursos        Oferta académica de un         id, codigo, nombre, creditos, cupoMaximo,
                periodo.                     cupoDisponible, periodo, docenteId, estado
 matriculas    Relación entre un estudiante   id, estudianteId, cursoId, periodo, estado
             y un curso en un periodo     (ACTIVA, CANCELADA), fechaMatricula
                (recurso asociativo).


Relaciones:

- Un docente dicta muchos cursos (1:N)

- Un estudiante tiene muchas matrículas (1:N)

- Un curso tiene muchas matrículas (1:N).

- Estudiantes y cursos mantienen una relación N:M resuelta por matriculas.

6. Caso en el que SOAP es conveniente
Escenario:

La universidad debe integrar el pago de la matrícula con el sistema de un banco (o con una
entidad gubernamental de reporte de información académica) que expone sus servicios mediante
SOAP. La operación consiste en registrar el pago, confirmar el recaudo y reportar la matrícula
como una sola unidad de trabajo.

Por qué SOAP es adecuado aquí:

    •  Contrato formal (WSDL/XSD): define de forma estricta operaciones, tipos de datos y
        errores, lo que reduce ambigüedades entre organizaciones distintas.
    •  WS-Security: permite firma y cifrado a nivel de mensaje, no solo del canal, algo exigido
      en entornos financieros y regulados.
    •  Transaccionalidad y fiabilidad: estándares como WS-AtomicTransaction y WS-
       ReliableMessaging garantizan que el pago y el reporte se completen o se reviertan juntos.
    •  Sistemas heredados: muchos sistemas empresariales y bancarios ya operan con SOAP, y
       reemplazarlos no depende de la universidad.
Cómo se combina con la API REST: la API de matrículas sigue siendo REST hacia los clientes
(web y móvil) y, internamente, un servicio adaptador consume el servicio SOAP externo. Así se
aprovecha la simpleza de REST en la interfaz pública y la robustez de SOAP en la integración
crítica.

7. Medida de seguridad: autenticación y autorización con JWT sobre HTTPS


Medida elegida:

===== PÁGINA 7 =====
Cada solicitud debe incluir un token JWT (JSON Web Token) firmado, obtenido tras iniciar
sesión, enviado en la cabecera Authorization: Bearer <token>. Todo el tráfico viaja cifrado con
HTTPS (TLS), y el servidor valida firma, vigencia y permisos del token en cada petición, sin
guardar sesiones (stateless).

Flujo:

    •   El usuario envía sus credenciales a POST /auth/login y recibe un token de acceso de corta
       duración (por ejemplo, 15 minutos).
    •   El cliente adjunta el token en cada solicitud a la API.
    •   El servidor verifica la firma y la expiración; si falla, responde 401.
    •  Se aplica control de acceso por roles (RBAC): si el rol no tiene permiso para la acción,
       responde 403.
 Rol              Permisos
 ESTUDIANTE     Consultar cursos; crear y cancelar sus propias matrículas; consultar su
                        perfil
 DOCENTE        Consultar sus cursos y las matrículas de ellos
 ADMIN            Crear, modificar y eliminar cursos; gestionar estudiantes, docentes y
                     matrículas

9. Interfaz web (front)
Además de la API se hizo un front sencillo en HTML y JavaScript, que consume los mismos
endpoints. Se sirve desde el mismo proyecto Laravel, así que no hay que instalar nada más: con
el servidor corriendo basta abrir http://127.0.0.1:8000 en el navegador.

Qué permite hacer cada rol:

                                       ADMIN: crear, editar y eliminar
                                                             cursos; registrar y eliminar
                                                             estudiantes y docentes; matricular
                                                        a cualquier estudiante y cancelar
                                                              matrículas.


                                     DOCENTE: ver los cursos, las
                                                            matrículas de sus cursos y la lista
                                                    de estudiantes.


                                        ESTUDIANTE: ver los cursos,
                                                              matricularse, ver sus matrículas y
                                                               cancelarlas.


El front guarda el token JWT que devuelve POST /auth/login y lo envía en cada petición. Los
errores de la API (cupo agotado, matrícula duplicada, permisos) se muestran como avisos al
usuario.
